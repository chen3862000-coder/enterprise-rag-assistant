# Retrieval Design

An authenticated query first passes through a bounded structured query planner when configured. The planner receives only the original user query and returns validated intent plus retrieval formulations; it cannot set identity or filters. The original query remains a baseline. Timeout, invalid output, disabled planning, or unavailable configuration uses a deterministic subject-preserving fallback. Each selected query is embedded with the separately configured Ollama model or searched through these parameterized PostgreSQL channels:

1. Exact cosine-distance search in pgvector.
2. PostgreSQL English full-text search over the generated `tsvector`.
3. Indexed multilingual lexical search over Latin terms and overlapping CJK bigrams.
4. Token-bounded exact search over indexed technical identifiers such as error codes and API identifiers; a shorter identifier does not match inside a longer token.

Every path applies the same document role, enabled-status, and active-version predicates in SQL. Only authorized candidates are returned to the retrieval service. Indexed lexical terms avoid CHM ancestor navigation paths; Java migration V21 also populates them for newly inserted/updated chunks. Reciprocal Rank Fusion merges lists without comparing incompatible raw scores and deduplicates on stable chunk IDs.

The deterministic evidence gate is shared by chat and offline evaluation. A candidate passes when a query contains exactly one recognized technical identifier that exactly matches authorized text, or when it has both a PostgreSQL full-text hit above the configured rank threshold and vector similarity above the configured threshold on the same chunk. Exact identifier bypass requires a structured identifier containing letters, or a named numeric status such as HTTP 429. It is disabled for queries containing sensitive requested terms such as credentials, secrets, salaries, and acquisition prices, and for multiple-identifier comparison queries, because substring matching cannot prove the requested fact is present. RRF score is not thresholded because it is a rank-fusion quantity, not a calibrated relevance probability. The gate returns a reason, filters the context to passing chunks, and an insufficient decision sends no source context to generation and returns no citations. Evaluation-only numeric diagnostics distinguish missing keyword signal, below-vector threshold, and split signals across candidates. Vector-only, keyword-only, and relaxed-threshold variants are diagnostic comparisons only; the runtime policy remains the current rule until precision/recall tradeoffs are reviewed on sufficient labeled data.

The active Nomic embedding setup still embeds raw text for both documents and queries. Nomic's published v1.5 usage recommends `search_document:` and `search_query:` task prefixes for retrieval. Java offline evaluation runs a paired shadow experiment: it embeds the currently authorized active chunks with `search_document:` and each query with `search_query:`, ranks those in-memory vectors, and measures Recall@5/MRR plus a diagnostic vector-only gate. This does not persist prefixed vectors, replace the active index, or affect chat. The Python evaluator marks prefix-shadow metrics unavailable. This is an initial corpus-specific experiment, not an operationally representative separate persistent index or production-policy approval.

The context assembler preserves fused order, applies a character budget, escapes source-supplied delimiter tags, and assigns citation IDs only to included chunks. Returned IDs must match supplied IDs. Citation resolution then re-checks authorized active source records. A valid citation means the source is real/current/authorized, not that every claim is factually correct. The API status is `CITATIONS_PRESENT`, deliberately not `SUPPORTED` or `GROUNDED`.

Exact vector search is intentional for the small MVP corpus. Bounded LLM query planning is distinct from answer generation and always retains the original query as a baseline. The planner can time out into deterministic fallback; evaluation forces deterministic mode. Cross-backend coverage calculations now use the larger English-stem or CJK-bigram term view, and one exact indexed identifier with vector support may use the exact evidence path. Authorization predicates remain SQL-controlled and identical on every retrieval path. Approximate indexes, rerankers, distributed search, and model-based retrieval judgments are not implemented.

Offline gate metrics use the pre-gate authorized fused candidates to determine whether relevant evidence was available, and separately record the post-gate admitted context. This distinction is required to count false abstentions correctly; a gate-rejected relevant candidate must not disappear from retrieval recall. Python persists both candidate and gate populations in its evaluation result. Java persists pre-gate retrieval candidates but does not yet persist per-query baseline/rewrite candidate IDs, limiting causal planner analysis. Runtime context remains post-gate only.
